# Extraction Audit — apps/desktop: MCP shim, transports, CLI, security, transactions

## SUMMARY

- The desktop app is the **only** externally addressable entry point into the editor agent layer. It runs a loopback-only JSON-RPC/MCP HTTP server inside the Electron main process (`src/main/mcp/http-server.ts`), plus a standalone stdio→HTTP shim published as a `bin` (`openreel-mcp`, `apps/desktop/package.json:7-8`) for clients like Claude Desktop/Cursor.
- Every `tools/list` and `tools/call` is forwarded verbatim to the **renderer** over IPC and executed against the shared `LiveEditorHost` (apps/web/src/services/agent/mcp-listener.ts:174-212). There is no filtering of the registry — all ~304 tools, including the raw `execute_action` / `batch_actions` escape hatches, are exposed.
- Authentication on the HTTP transport is a single static-per-session Bearer token written to `%HOME%/.openreel/mcp-endpoint.json` (0600) and read by any local process; the token is also surfaced to the renderer and shown/copyable in Settings.
- MCP tool calls are **fire-and-forget per call**: no transaction grouping crosses the MCP/IPC boundary. Atomicity exists only in the in-app chat agent loop (`packages/agent/src/loop.ts`), which wraps each turn in begin/commit/rollback — external MCP agents get none of that.
- aurora-host is neither HeadlessHost nor LiveEditorHost: it is a forked Node child process that renders Motion-Creator "Aurora" frames off-process using a native ray-tracer binary (spawned per render with a custom magic-byte protocol), with session management via IPC.

## FINDINGS

1. **MCP HTTP server binds loopback by default, port random or `OPENREEL_MCP_PORT`.** apps/desktop/src/main/mcp/server.ts:47-49, 75-80; http-server.ts:84,131. Confidence: high.
2. **Bearer token required on every request including `tools/list`; compared with `timingSafeEqual`; read live so rotation takes effect without restart.** http-server.ts:51-64,91; server.ts:23-24. Tests pin 401 without/wrong token, token rotation, 405 non-POST, 202 notifications, batch handling: src/main/mcp/http-server.test.ts:40-130. Confidence: high.
3. **Request body capped at 4 MB; single-shot request/response only — no GET/SSE/streaming/WebSocket endpoint anywhere in main** (grep for `createServer`/`WebSocketServer` in apps/desktop/src finds only http-server.ts). http-server.ts:5,24-40; core.ts handles only `initialize`/`ping`/`tools/list`/`tools/call` (+notifications) core.ts:124-164. Confidence: high.
4. **stdio shim (`openreel-mcp`) reads `{url,port,token}` from `~/.openreel/mcp-endpoint.json` and POSTs each stdin NDJSON line as JSON-RPC with the Bearer header; response lines are echoed to stdout.** mcp-shim/index.ts:14-22 (readEndpoint), 24-64 (postRpc + Authorization), 101-127 (readline loop); endpoint path fixed at shared/mcp.ts:16-20 (`OPENREEL_MCP_ENDPOINT_FILE` override). Endpoint file written 0600 at server startup, removed at quit: server.ts:51-61,63-69,82-87,89-97.
5. **`forwardLine` contract pinned by tests:** blank lines dropped; unparseable lines dropped without POST; notification posts returning null emit nothing; failed requests become JSON-RPC error code `-32000`; errors for notifications are swallowed. src/mcp-shim/forward.test.ts:5-48; implementation mcp-shim/index.ts:71-99. Confidence: high.
6. **No tool filtering at any layer:** renderer returns `toMcpTools()` unfiltered (mcp-listener.ts:178-180 → packages/agent/src/registry.ts:31895-31903); dispatcher/main forward unchanged. Destructive flags exist in the registry but are NOT part of the MCP schema output. Confidence: high.
7. **Executor authority = renderer's LiveEditorHost.** Main → `win.webContents.send(CHANNELS.mcpRequest)` (renderer-bridge.ts:41-52) → preload `onRequest` bridging to page world (preload/index.ts:128-157) → `handleMcpBridgeRequest` → `runExclusive(() => executeTool(name,args,getLiveEditorHost()))` (mcp-listener.ts:194-203) → project-store action execution. Confidence: high.
8. **Timeouts:** `listTools` 10 s; `callTool` 120 s standard, 30 min for a hardcoded set of 11 long-running tools (`export_video`, `transcribe`, `upscale`, …). renderer-bridge.ts:19-33,55-68; timeout/reject logic dispatcher.ts:39-59 with unit tests dispatcher.test.ts:51-74. Timed-out calls leave the renderer work running (no cancellation signal is sent downstream). Confidence: high.
9. **Destructive/expensive gating depends on a user setting that defaults ON.** If `mcpAutoAllowTrustedLocal` is false, destructive/expensive tools return `CONFIRMATION_REQUIRED` instead of executing (mcp-listener.ts:184-196); default is `true` (apps/web/src/stores/settings-store.ts:129). So out-of-the-box, any local process holding the token can call destructive/expensive tools unattended. Confidence: high.
10. **MCP server requires an open editor window even for `tools/list`.** `targetWindow()` throws "No editor window is open" when no BrowserWindow exists (renderer-bridge.ts:35-38,44-48) → surfaces as `-32603`. Confidence: high.
11. **Headless desktop operation does not exist:** apps/desktop never imports `@openreel/agent`'s HeadlessHost; everything goes through the GUI window's renderer. Evidence: imports across src/main/mcp + tsup.config.ts entries; no `headless-host` import found under apps/. Confidence: high.
12. **Full zod-validated IPC surface registered at boot** (58 named channels): hardware probe, fs dialog/read/write/chunked-write/reveal/temp, keychain get/set/delete, export start/audio chunks/cancel, aurora preview+sequence sessions, media proxy/transcode/audio-extract/probe/fetch-url, rigging probe/rig, cloud fetch, gpu upload/submit/status/artifact/cancel, window controls, lifecycle unsaved-guard/flush, updater status/download/install, crash report, mcp status/rotate/test. apps/desktop/src/main/index.ts:175-313; channel names shared/channels.ts:1-59. A few handlers bypass the schema wrapper (`auroraStart*`, `exportStart`, `windowControl` parses inline, `crashReport` fire-and-forget on raw `.on`). index.ts:209-236,270,287-294,294-310.
13. **Token exposed to renderer and UI:** `mcpGetStatus` returns the live token (server.ts:99-108 → main/index.ts:311), preload exposes it (preload/index.ts:154), settings panel displays/copies it (apps/web/src/components/editor/settings/McpPanel.tsx:119-206). Confidence: high.

## TXN-SEMANTICS

- **MCP calls carry no transaction grouping.** The wire protocol admits only `name`+`arguments` (core.ts:148-160; shared/mcp.ts:30-35). `handleMcpBridgeRequest` executes exactly one tool per request and never touches `beginTransaction`/`commitTransaction`/`rollbackTransaction` (mcp-listener.ts:181-204). An external multi-tool agent turn is therefore N independent undoable actions, **not atomic**; a mid-turn failure leaves prior actions applied and simply reports `ok:false` to the agent (executeTool catches handler exceptions into `TOOL_ERROR` results rather than throwing, executor.ts:32-52).
- **The only rollback machinery is in the in-app chat loop**, not reachable from MCP: `loop.ts:116` opens `host.beginTransaction(turnLabel)`, commits on success/budget/limits (loop.ts:124,144,245,257) and rolls back when the turn *throws* (loop.ts:267). Note individual failing tools do NOT throw — they return error ToolResults — so partial edits within an otherwise-successful chat turn are committed too, by design ("whole turn undoes as one history group", live-host.ts:141-143).
- **LiveEditorHost rollback is weak vs HeadlessHost:** it ends the history group and issues a single `undo()`, gated on its own `appliedInTxn` counter (live-host.ts:153-184). HeadlessHost instead snapshots the whole project pre-turn and restores wholesale precisely because inverse-replay/history-trimming can defeat undo (packages/agent/src/headless-host.ts:42-69 comment). Project stores without adequate history depth, or jobs run outside applyAction (exports, GPU jobs, motion renders — live-host.ts:186-190), are outside any rollback.
- **`batch_actions` has no compensating action on failure** — it stops at first failure but does not undo actions already applied (registry.ts:31539-31562).
- **Serialization exists where atomicity matters most:** `runExclusive` chains every chat-turn and every MCP call through one promise queue so undo groups cannot interleave (host-singleton.ts:14-27, wired in mcp-listener.ts:199-201 and DesktopApp.tsx:71-76).
- **Cancellation semantics differ by subsystem:** long-running MCP calls time out in main but the underlying render keeps running with no cancel path (renderer-bridge.ts:39-68; no abort propagation in dispatcher). Exports have explicit cancel channels and cleanup on quit (index.ts:286,361-365); aurora sessions use AbortControllers (aurora-host/index.ts:47-49,62-85).

## SECURITY

- **Renderer privileges are locked down:** `contextIsolation:true, nodeIntegration:false, sandbox:true, webSecurity:true` (index.ts:159-165). Content loads only from a privileged custom scheme `app://openreel` with path-traversal guard and COOP/COEP/CORP headers (protocol.ts:7-53).
- **Navigation hardening:** same-origin gate on `will-navigate`/`will-redirect`; popups denied with https URLs opened in the default browser instead (nav-guard.ts:23-38; test nav-guard.test.ts). External content can't reach the renderer ordinarily.
- **Preload exposure surface is large and privileged** — this is the blast radius if renderer XSS ever occurs: arbitrary-path file read/write (`fs.readFile`, `fsWriteFile`, chunked writers — no directory allowlisting; fs.ts:12-88; schemas just `z.string()` paths, ipc-contract.ts:34-35), OS keychain secrets get/set/delete (preload/index.ts:28-32), cloud fetch proxy injecting stored API keys (cloud.ts:9-38), ffmpeg operations, Blender rigging exec, GPU job uploads/downloads, updater install, MCP status incl. token. Grep shows **no CSP header and no `session.setPermissionRequestHandler`** anywhere (main or web index.html).
- **Outbound URL fetch (`mediaFetchUrl`) has real SSRF hygiene:** https/http only, blocks loopback/link-local/private ranges unless `OPENREEL_ALLOW_LOCAL_FETCH=1`, size cap with declared-length precheck (fetch-url.ts:18-61) — notable caveat: hostname checked before resolve (no DNS-rebinding defense) and redirects followed.
- **Transport auth strength:** good mechanics (timingSafeEqual, rotation support, loopback bind) but two structural weaknesses: (a) token lives in a home-dir file readable by any process running as the same user, and by design must be since external local MCP clients need it (server.ts:51-61); (b) the full token is handed to the renderer and displayed in Settings (FINDINGS #13), so any renderer compromise yields drive-everything authority over the editor including `CONFIRMATION_REQUIRED` bypass once `mcpAutoAllowTrustedLocal` default stands.
- **Unsafe-for-agent primitives reachable through MCP:** `execute_action` dispatches any editor Action by string type with raw params (registry.ts:31515-31537, flagged destructive); `rig_humanoid_model` spawns headless Blender with generated Python (sidecar/rigging-backend.ts); fs-bound flows triggered via tools write files at renderer-chosen paths (e.g., exports choose paths via native dialogs or tempfiles, but project IO is unrestricted). All gated only by the default-on auto-allow flag.
- **mcpResponse listener accepts responses from any webContents without checking `event.sender`** (renderer-bridge.ts:50-51) — currently safe because one window exists, but fragile if second windows/webviews appear.

## GAPS

- No streaming/progress protocol on MCP: 30-min blocking waits for exports/previews; no job handle returned early; no polling surface documented for `export_*` intermediate progress. (core.ts single response; renderer-bridge LONG_RUNNING_TIMEOUT_MS.)
- No transaction envelope across MCP/IPC (no batch-run wrapper analogous to loop.ts) despite both hosts implementing the EditingHost txn interface — cross-turn atomicity impossible for external agents.
- `tools/list` requires a GUI window; there is no headless mode of the desktop MCP for CI/background use.
- No rate limiting or concurrent-call caps at HTTP layer beyond 4MB body; batches fan out with `Promise.all` (http-server.ts:71-78) though execution serializes at the renderer queue.
- No clipboard/permission/popup hardening config beyond nav-guard; no CSP headers; no permission-request handler.
- No token TTL/auto-rotation; rotation is manual-only via UI (server.ts:110-119).
- Desktop fs IPC lacks path scoping/allowlist — fine for a trusted UI, limiting for a stricter extraction boundary.
- DISTRIBUTION.md notes identity mismatch (`com.openreel.video` GPU bundle id vs appId `video.openreel.desktop`, DISTRIBUTION.md:148-150).

## FACADE-NOTES

Implications if a facade (HTTP/orchestration service) is placed over these transports:

- **Auth:** today the boundary is "same user, knows token". A facade should (a) terminate auth itself and hold the OpenReel token server-side rather than exposing the endpoint file pattern further; (b) fix the default-on auto-allow into an explicit per-client grant list (the CONFIRMATION_REQUIRED mechanism, mcp-listener.ts:184-196, is the natural hook); (c) stop returning tokens via status endpoints. Keep loopback binding as defense-in-depth.
- **Atomicity:** expose transactions at the facade level — either add a txn kind to the MCP bridge (`beginTransaction/commit/rollback` already exist on EditingHost and are unused for MCP), or drive `rollbackTransaction` after detecting turn failure via history-group undo. Prefer HeadlessHost-style snapshot semantics; LiveEditorHost's undo-based rollback fails under history trimming/inverse-handler exceptions (headless-host.ts:42-54 explains why). `batch_actions` should wrap its loop in a group + compensating undo before being offered as a facade bulk primitive.
- **Idempotency:** tool handlers mint fresh action ids internally (`genId()`, e.g. execute_action registry.ts:31519-31521), so re-delivered MCP calls create duplicate state — facade must attach client-supplied request ids (extend `McpBridgeRequest.callId` idea upstream into a per-action idempotency key) and dedupe. Long-running jobs (export/preview/GPU) need facade-visible job handles instead of 30-minute synchronous holds, plus an explicit cancel verb propagating AbortController (pattern already present in aurora sessions and exports).
- **Process model:** a facade that needs headless operation cannot reuse the desktop path (window required). Recommend routing facade traffic at `toMcpTools()`+`EditingHost` level against HeadlessHost-style snapshotting executor, keeping LiveEditorHost for interactive parity; the desktop renderer-bridge/dispatcher shape (`listTools`/`callTool` + callId correlation) is already the right seam to replicate.
