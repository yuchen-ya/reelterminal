# Extraction Audit — Area: packages/core action system (executor, validator, handlers, history, inverse integrity) + capabilities/manifest

Baseline: 2566c34e0f8ea22992a85f3ff16e048307b49365 (branch audit/extraction-2566c34). Read-only audit; nothing committed. Mechanical data cross-referenced from audit/action-map.jsonl (110 types: 36 registry + 74 executor-switch, disjoint sets, no type handled by both).

## SUMMARY

- Dispatch is a two-tier "registry handler first, prefix-switch fallback" chain repeated identically in all three layers: `ActionValidator.validate` (action-validator.ts:40-43), `InverseActionGenerator.generate` (inverse-action-generator.ts:24-27), `ActionExecutor.applyAction` (action-executor.ts:248-255). No action type is handled by both a registry handler and an executor switch case (map confirms 36+74 disjoint).
- `execute()` flow is strictly sequential and mutates the project IN PLACE with no rollback on failure: validate → JSON deep-clone snapshot → generate inverse from the snapshot → apply → resolve `__LAST_ADDED__` markers in the inverse → history push (action-executor.ts:85-127). A throw inside apply returns an error ActionResult but leaves any already-applied partial mutation unrolled.
- `executeMany` is best-effort stop-on-first-failure, NOT atomic: each action commits independently to project + history; earlier actions survive a later failure (action-executor.ts:129-144).
- Undo replays stored inverse actions WITHOUT re-validation; null-inverse entries silently contribute nothing yet are still popped onto the redo stack — undo of a null-inverse group returns an error but creates bogus redo availability that would double-apply original effects (action-history.ts:233-263, action-executor.ts:146-183).
- Interpreting the 77 dummy-null invert probes: most are GENUINE inverses that only see no target because `{}` params name no entity. After source review the genuinely-missing inverses are concentrated in clip editing ops (`clip/merge`, `clip/slip`, `clip/slide`, `clip/roll`, `clip/trimToPlayhead`) plus all undo-machinery restore types; only `project/create` is by-design non-invertible.
- Validator coverage is better than the raw case-count suggests but still has hard holes: unknown PREFIX is rejected, known-prefix-unknown-type passes with ANY params (zero `default:` branches in validator switches), and exactly 19 of 110 types have no validation at all beyond the shape check.
- HeadlessHost transaction = full structuredClone snapshot + `history.clear()` on rollback (robust, but nukes ALL pre-turn history); LiveEditorHost rollback instead relies on one history-group undo and is defeated by any null-inverse action in the turn. Two hosts, divergent rollback semantics.
- CAPABILITY_MANIFEST is a static vocabulary/enums manifest (blend modes, effect defs, ranges, presets), consumed by the agent's `get_capabilities` tool — it maps to no actions or tools directly.

## FINDINGS

1. **Dispatch precedence — registry first everywhere.** All three layers call `getActionHandler(type)` before their own switch: validator action-validator.ts:40-43 (`return handler.validate(...)` — handler validation REPLACES category validation entirely via early return), inverse generator inverse-action-generator.ts:24-27, executor applyAction action-executor.ts:248-255 (handler path also skips the shared suffix logic? No — it recalc durations at :253 then returns early). The 36 handlers register themselves via side-effect import `"./handlers"` (action-executor.ts:49, handlers/index.ts:1-5). Confidence HIGH.

2. **execute() flow, exact order** (action-executor.ts:85-127):
   - L86-97 validate; failure → `{success:false, code:"INVALID_PARAMS", details:{errors}}`.
   - L98 `projectSnapshot = JSON.parse(JSON.stringify(project))` — lossy JSON clone (Blob/File become `{}`, Float32Array waveform becomes object/array-of-numbers; functions dropped).
   - L99-102 `inverseGenerator.generate(action, projectSnapshot)` — runs OUTSIDE the try block; an exception here escapes as a rejected promise (no ActionResult).
   - L104 applyAction inside try; throw → caught L117 → `{success:false, code:"INVALID_PARAMS"}`; NO history entry pushed, but partial in-place mutation is NOT rolled back.
   - L108-110 `resolveSpecialMarkers(inverseAction)` resolved eagerly while this action's created entity is still latest (see #5).
   - L111 `history.push(action, resolvedInverseAction)`. Confidence HIGH.

3. **executeMany = best-effort, not atomic** (action-executor.ts:129-144): plain `for` loop over `execute()` per action; on first failure it `break`s, returning the results so far. No grouping wrapper, no pre-flight validation pass, no snapshot/rollback. Already-applied actions remain applied AND remain on the undo stack individually (grouped only if a caller began a group externally). The agent's `batch_actions` tool compounds this: it iterates `host.applyAction` per item and stops on first failure with `BATCH_FAILED`, leaving earlier steps live (packages/agent/src/registry.ts:31539-31562). Confidence HIGH.

4. **ActionHandlerContext.lastAddedIds purpose** (registry.ts:4-6, action-executor.ts:56,227-240): a Map keyed by entity CATEGORY (`action.type.split("/")[0]`: media, track, clip, marker, effect, keyframe, subtitle, transition) holding the id of the most-recently CREATED entity of that category, recorded by executor cases at creation time (e.g. media/import :378, track/add :459, clip/add :730, marker/add :613, effect/add :1262, keyframe/add :1439, subtitle/add :1829, transition/add :1536, clip/split second-half :843). It exists to substitute the literal `"__LAST_ADDED__"` sentinel that inverse params carry for add-type actions whose ids are generated inside apply() — e.g. inverse of `clip/add` is `{type:"clip/remove", params:{clipId:"__LAST_ADDED__"}}` (inverse-action-generator.ts:358-361). Resolution happens right after THIS action applies (:108-110) so the STORED inverse is durable against later adds; a second resolution pass runs again at undo time (:170) but is then a no-op for correctly-resolved markers. Handlers never read/write it (overlay/motion/bulk-set creation handlers embed explicit ids instead). Confidence HIGH.

5. **Undo pipeline** (action-executor.ts:146-183 + action-history.ts:233-295): `history.undoGroup()` pops the last contiguous run of same-groupId entries (or the single entry); for each returned inverse it re-resolves markers and calls `applyAction` DIRECTLY — validation is skipped entirely on undo, locked-track checks included; undo application errors that occur mid-loop leave earlier inverses of the group applied with no rollback. Redo re-applies ORIGINAL actions the same way (:185-221). Confidence HIGH.

6. **What history.push(action, null) means** (action-history.ts:160-217, 233-263): the entry IS stored (with `inverseAction:null`) and makes `canUndo()` true. At undo time `undoGroup()` filters nulls out (`if (action)` :260). Consequences:
   - Single-entry history: `undoGroup()` → `[]` → executor.undo fails with "No inverse action available" (:158-166) BUT the entry was ALREADY popped onto redoStack inside `undo()` (:234-240 pops before checking the inverse). Result: a failed undo consumes undo state AND arms a redo that REAPPLIES the original never-undone action (double-apply; e.g. two `clip/merge` runs back-to-back, double volume-set). 
   - Mixed groups (one undoable edit + one null-inverse op in the same txn group): undo proceeds silently applying only the real inverses; redo then reapplies ALL originals including the never-undone null one. There is no surface anywhere that reports "this entry has no inverse". Confidence HIGH.

7. **History internals**: auto-grouping window default 100ms (`autoGroupWindow`, :145), restricted to AUTO_GROUPABLE_TYPES slider-style set (:92-113) and requires same-type + same-target-id (TARGET_PARAM_KEYS :117-124; check :176-192). Manual grouping via beginGroup/endGroup tags every push made between them (:194-201, groupId inherited at :176). Trimming: maxHistorySize=1000 default (:147); when exceeded, oldest entry is shifted off and snapshots are index-shifted then filtered below 0 (:209-214) — old entries (and their inverses) are gone, matching standard editor behavior, but a snapshot AT the trimmed boundary dies rather than re-pointing. `setMaxHistorySize` trims WITHOUT adjusting/removing stale snapshots (:393-399) — inconsistent with the push-path trimming. Snapshots (createSnapshot/deleteSnapshot :297-321) are pure index markers over the undoStack — there is NO restoreSnapshot implementation anywhere in core; nothing can jump back to a snapshot, they're display/bookkeeping only (getDisplayHistory :323-339 dedupes groups). Subscribers notified on push/undo/redo/group-end/clear/snapshot-changes, but NOT on setMaxHistorySize/setAutoGroupWindow. Confidence HIGH.

8. **HeadlessHost transactions** (packages/agent/src/headless-host.ts:44-70): beginTransaction deep-clones the whole project via structuredClone (:49) and opens a history group (:50). rollbackTransaction ends the group, swaps in the snapshot, and calls `history.clear()` (:59-69) — wiping undo AND redo stacks INCLUDING everything before this turn. Mid-group interaction: because clear() resets `currentGroupId` (:365) there is no dangling open group afterward; endGroup() before the clear guards against pushing further entries into the aborted group. Nested transactions are unguarded — an inner endGroup clears currentGroupId while an outer txn believes itself open, after which subsequent pushes join no group (irrelevant headlessly since rollback clears all anyway). Contrast LiveEditorHost (apps/web/src/services/agent/live-host.ts:161-185): no snapshot; rollback = endHistoryGroup + ONE store undo() which only works if every successful action in the turn had a real inverse AND stayed grouped — any null-inverse action breaks the rollback (partial revert). Confidence HIGH.

9. **Handlers inventory (36 registered across 5 modules)**:
   - handlers/clip-fx.ts (8): `clip/setSpeed` (+derived duration rewrite :32-42), `speed/setRampData` (writes THREE clip fields in one unit :74-86), factory-made field setters `clip/setReverse|setPitchCorrection|setStabilization|setChromaKey`, `speed/setKeyframes→speedKeyframes`, `speed/setFreezeFrames` (:105-154).
   - handlers/bulk-set.ts (9): `keyframe/setAll` (replaces whole keyframes array), `effect/setOrder` (permutation reorder), `effect/setStack` (structuredClone replace whole effect list), `subtitle/replace`, `subtitle/setAll` (replaces timeline.subtitles wholesale), `adjustment/setAll`, `mask/setAll`, `multicam/setAll`, `nested/setAll` (writes TWO top-level project arrays compoundClips+nestedInstances). setAll validate()s are constant true except setOrder.
   - handlers/overlay.ts (12): factory `makeOverlayHandlers(prefix,field)` × {text,shape,svg,sticker} → create/update/remove over TOP-LEVEL project fields textClips/shapeClips/svgClips/stickerClips (:135-140,17-28) — these entities do NOT live in the timeline like normal clips.
   - handlers/motion.ts (5): composition upsert/create/remove + instance insert/remove; removeComposition CASCADES (also deletes every instance AND their timeline clips via removeMotionInstance :120-140 called in loop :123-139); removeInstance likewise deletes dependent timeline clips filtered by metadata.motionInstanceId (:27-31).
   - handlers/creation.ts (2): `creation/replaceState` / `creation/applyOperation` — Object.assign ENTIRE nextProject onto the live project (:22-24,71-77); op application validated by dry-run through applyCreationOperation before commit (:99-110).
   - Mutation-beyond-stated-scope notes: motion/removeComposition+removeInstance wipe dependent clips (by design cascade but worth gating); clip-fx setSpeed also rewrites duration; applyClipAction's move/trim/slip/trimToPlayhead suffix additionally syncs project.nestedInstances shells (action-executor.ts:1196-1221); bulk-set setAll handlers replace whole collections; creation handlers assign whole-project objects. Confidence HIGH.

10. **capabilities/manifest.ts**: exports `CAPABILITY_MANIFEST` (:335-360) — a frozen vocabulary: blendModes, videoFilterTypes, audioEffectTypes, transitionTypes, easings, shapeTypes, filterPresets/textAnimationPresets summaries, speed range+curve presets, colorGrading numeric ranges (:266-273), full `effects: EffectDefinition[]`, a large `motion` sub-manifest (:201-264: layer types, 24 effect types, expressions, particle/light/ui vocab, font families, style feature flags) and a `creation` sub-manifest (:275-333 incl. the 10 operationTypes consumable by creation/applyOperation). It contains NO action types, NO tool names, NO schema logic. Consumption: `EditingHost.capabilities()` contract (packages/agent/src/host.ts:209) implemented by both hosts returning this constant; surfaced to the model via the read-only tool `get_capabilities` (packages/agent/src/registry.ts:~10686 "Valid enums + parameter ranges") and baked into generated docs (packages/agent/src/gen-docs.ts:24-30). So its mapping role is "enum/range reference for parameter construction", orthogonal to dispatch. Confidence HIGH.

11. **action-serializer.ts purpose** (action-serializer.ts:1-49): tiny utility class for JSON round-tripping Action objects (serialize/deserialize/serializeMany/deserializeMany) with only structural checks on deserialize (type/id/timestamp strings-or-number and params object) — no schema or registry awareness, no integration into the executor/history (grep finds no production callers in core beyond export in actions/index.ts; persistence layers use their own code). Use case: replay logs / cross-process action transport. Confidence MEDIUM (absence verified by grep only).

## VALIDATOR-GAPS

Coverage accounting over the 110 types (audit/action-map.jsonl): 52 types hit `validator_switch_case=true`; 36 registry-handler types are validated by `handler.validate` instead (validator.ts:40-43); keyframe/add|remove|update are covered by SHARED PRE-SWITCH CHECKS in validateKeyframeAction, not case labels (action-validator.ts:956-1004 — clipId string + clip exists + TRACK_LOCKED + property/time required), which explains them being flagged uncovered mechanically. That leaves exactly 19 of 110 truly unvalidated:

- Audio/media restores: `audio/restoreEffect` (executes regardless of clip presence), `media/restore`.
- Clip gap/edit ops validated-as-valid with ANY params: `clip/closeGapBefore`, `clip/merge`, `clip/roll`, `clip/slide`, `clip/slip`, `clip/trimToPlayhead`.
- Pure restore types: `clip/restore`, `clip/rippleRestore`, `effect/restore`, `marker/restore`, `subtitle/restore`, `subtitle/restoreAll`, `track/restore`, `track/restorePositions`, `transition/restore`, `transition/restoreTrack`.

Evidence of pass-through: validateClipAction has NO case for merge/slip/slide/roll/trimToPlayhead → switch exits → `return errors` empty at action-validator.ts:789 → execute proceeds. None of the sub-validators define a `default:` branch (grep "default:" in action-validator.ts → zero hits).

Unknown-type semantics (action-validator.ts:57-93):
- Type WITHOUT a known prefix (not project/|media/|track/|clip/|effect/|transform/|keyframe/|transition/|audio/|subtitle/|marker/) → REJECTED, `UNKNOWN_ACTION_TYPE` (:87-92). Note this rejects ALL registry-handler prefixes that are not in that list too... EXCEPT handlers intercept first (:40-43), so adjustment/, mask/, motion/, multicam/, nested/, speed/, creation/ (and more) validate via their handlers. A NON-registered invented prefix like `foo/bar` is rejected; a KNOWN-prefix garbage type like `track/hogwash` is silently ACCEPTED (pass-through → executor switch does nothing → recalc duration → success:true with no-op!). Combined with missing defaults, `clip/add` typo'd as `clip/addd` reports success. For agents this means silent no-op success instead of an error.

Also of note: registry-handler types skip ALL category-level context checks (no locked-track check for clip/setSpeed etc.; handlers do their own findClip check but none check track.locked) — inconsistent guard strength vs switch-validated types (validators push TRACK_LOCKED at e.g. action-validator.ts:1180-1185).

## GAPS

G1. No `default:` branches anywhere in validator switches (verified) — known-prefix typos silently succeed as no-ops (returning success:true), defeating optimistic agent retry loops.
G2. Undo-machinery restore types and the four missing-invert edit ops are pushable INTO history when executed directly (they pass validation), permanently losing undo capability for those steps (see RISKS).
G3. Three inverse generator methods (marker/media/transition) fall off the switch without `return null`, yielding `undefined` (probe "undefined" rows); harmless due to falsy-checks at action-executor.ts:108/158 but inconsistent with siblings.
G4. Two cast-labeled generator cases (`as TrackAction["type"]` / `as ClipAction["type"]`) defeat static analysis (audit/action-map.jsonl marks inverse_generator_case=false for track/consolidate & clip/closeGapBefore despite real code at inverse-action-generator.ts:334-346/469-482) — any downstream tooling built off case-label greps inherits this blind spot.
G5. registry.createInverseAction helper (registry.ts:33-44) is dead code — all producers build inverse literals inline (grep found no callers outside tests/generated code); drift risk between canonical fields.
G6. ACTION_DESCRIPTIONS in action-history.ts mentions `clip/duplicate` (:35) which is neither in the 110 union nor executed anywhere in core — dead description; duplicate must be implemented above the core (untracked by history if done ad-hoc).
G7. Keyframe identity is `keyframe-${Date.now()}` (action-executor.ts:1424): two adds in the same millisecond collide on id; inverse lookup sidesteps ids by using property+time, but batch inserts can produce duplicates.
G8. Snapshot bookkeeping inconsistency: `setMaxHistorySize` trims the stack but leaves stale snapshots (action-history.ts:393-399), unlike push-path trimming which shifts them (:209-213).

## RISKS

CORE-01 (HIGH) Non-atomic multi-step edits are presented as if atomic nowhere. `executeMany` stops on first failure leaving partial work applied + journaled (action-executor.ts:135-141), and `batch_actions` exposes this directly to the agent (packages/agent/src/registry.ts:31550-31561) while the loop may roll back only on thrown exceptions (the loop treats action-level failures as committed — packages/agent/src/loop.ts:267 rollback triggers on throw only). An agent that builds "add track → add 10 clips" batches gets half-built timelines on failure #7 with success-reported steps already irrevocable except via manual compensations.

CORE-02 (HIGH) Null-inverse undo trap / poisoned redo. Any executed action lacking an inverse (project/create, clip/merge, clip/slip/slide/roll/trimToPlayhead, direct restore types, mask-cascade failures) yields `canUndo()===true` with undo being either a no-op-with-error + armed-redo (single-entry: pop + redo-stack push, action-history.ts:233-241) or a SILENTLY SKIPPED entry inside groups (:260). A subsequent redo() re-executes the never-undone original → double-apply corruption. Agent facades that offer "undo my turn" inherit this. Evidence: action-executor.ts:157-182, action-history.ts:260.

CORE-03 (MEDIUM) Inverse generation sits OUTSIDE try/catch (action-executor.ts:98-102). Today's throws are all pre-gated by validate(), but any handler/generator that dereferences optional nested state (pattern seen in 10/110 probes) turns `execute()` into a rejected promise (host.applyAction throwing ⇒ TOOL_ERROR upstream, no ActionResult contract) — and in the LIVE host path that exception during a turn is exactly what triggers rollback-with-clear, amplifying blast radius. Low likelihood today, high tail severity.

CORE-04 (MEDIUM) Undo bypasses validation and tolerance (action-executor.ts:170-171): inverse apply goes straight to applyAction. Re-adding a deleted clip whose track was meanwhile removed lands it on a nonexistent track (`clip/restore` maps only tracks matching clip.trackId — silently drops the clip), removing transitions/objects already gone are silent no-ops; partial multi-step undo mid-failure can't resume cleanly. State-drift between edit-time and undo-time is never detected (no precondition digests in HistoryEntry).

CORE-05 (MEDIUM) Divergent rollback semantics between hosts. HeadlessHost: full snapshot + history.clear() (robust but destroys ALL pre-existing undo history, breaking user expectation of long-lived undo in CLI sessions; headless-host.ts:63-69). LiveEditorHost: rely-on-one-group undo (live-host.ts:178-185) — broken by ANY null-inverse action executed in the turn (turn edits survive rollback silently). Same EditHost interface, opposite guarantees.

CORE-06 (MEDIUM) Lossy project snapshot used to construct inverses (action-executor.ts:98). Undo of media/delete resurrects an item whose Blob/File was destroyed by JSON round-trip (cloneMediaItem copies item.blob from the snapshot — inverse-action-generator.ts:205-212,832-845): playback-dependent features break after such undos. Also freezes Date-derived values and drops prototype data. Same cloning caveat applies to waveformData Float32Array (rebuilt as plain array — cloneMediaItem :841-844 re-wraps only what survived).

CORE-07 (LOW-MEDIUM) Partial mutation on failed apply. Executor cases mutate progressively then may throw late (e.g. structuredClone inside track/duplicate, assignProject paths) — catch at :117-126 returns failure but keeps the intermediate writes. Core offers no rollback helper (that's why HeadlessHost clones).

CORE-08 (LOW) Validation asymmetry invites agent no-ops: known-prefix unknown types succeed silently (VALIDATOR-GAPS/G1) — combined with `additionalProperties:true`-style loose schemas upstream, an agent mistyping one action type burns a step and cannot distinguish success from effect.

CORE-09 (LOW) Flawed-ish inverses: subtitle/setStyle (first-subtitle style only, :802-807 vs all-subtitle apply at executor :1877-1884), keyframe id collisions within same ms (:1424), motion/removeInstance inverse recreates (not byte-restores) dependent clips via insertInstance (acceptable approximation; evidence motion/motion-engine.ts:211-251).

## FACADE-NOTES

F1. Atomicity must be provided by the facade, not assumed: prefer HeadlessHost-style beginTransaction(snapshot)+commit/rollback around every agent batch (loop.ts already wraps turns; keep executeMany out of critical paths and drive single `applyAction` steps inside the txn instead). On HEADLESS-style hosts rollback also erases all older undo history — decide whether that is acceptable product behavior for CLI/cloud sessions or whether history.clear should preserve pre-turn entries (e.g., truncate to a saved stackIndex via getUndoStackSize()).

F2. If facades expose generic execute_action/batch_actions, PRE-FILTER the 8 truly-uninvertible payload types (project/create, clip/merge, clip/slip, clip/slide, clip/roll, clip/trimToPlayhead + 12 restore types) — either reject, warn in ToolResult, or mark those history entries explicitly (extend HistoryEntry with `undoable:false` + gate undoGroup counting), so undo chains never contain a hollow link (fixes CORE-02 surface at facade level).

F3. Revision semantics: the system has no revision numbers or content hashes; "state version" must come from the facade (e.g., incremented counter on each successful execute + structuredClone fingerprint). Return created-entity ids to the agent explicitly from applyAction results — the internal `lastAddedIds` channel is deliberately per-call-scoped (resolved into stored inverses, action-executor.ts:108-110) and never surfaced through ActionResult, so a facade's "give me the new clipId" requirement needs its own mechanism (query by lastAddedIds snapshot immediately after the call works because it is monotonic per category).

F4. Undo/redo reuse the SAME dispatch chain minus validation (CORE-04/06). A strict facade should re-validate inverse batches before applying (cheap) and treat undo-failure as "manual repair needed" rather than partial progress. For lossless undo of media-bearing entities, consider switching snapshot strategy from JSON.parse(JSON.stringify()) to structuredClone in execute() (mirroring HeadlessHost.beginTransaction) — small change, fixes CORE-06.

F5. Silent-success no-ops (unknown-prefix typos rejected, known-prefix garbage accepted) are a trap for autonomous loops: facades should enforce their OWN allowlist of the 110 types at the boundary and diff-check (state changed?) after each write if reliability matters more than throughput.

F6. Two-host divergence (CORE-05) means any facade guarantee ("rollback reverts your turn") holds only where Host implements it with a snapshot; document/test per-host rather than claiming interface-level behavior from EditingHost alone (packages/agent/src/host.ts:205).
